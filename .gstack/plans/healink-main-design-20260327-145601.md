## Problem Statement

当前创作流程已经有五个节点和前端工作台，但后端业务逻辑仍是本地 mock provider 串行执行：

- `剧情提炼`
- `歌词结构`
- `编曲设定`
- `封面方向`
- `音频渲染`

这次要解决的问题不是“再加一个 AI 接口”，而是把这条链路升级成一条**真实的文本工作流**：

- 输入一个电影题材后，五个节点都能稳定跑完
- 每个节点都依赖前一个节点的产物
- 每个节点都输出结构化、专业、可展示的工作台 artifact
- 即使图片和音频还没有真实生成能力，后两个节点也要变成真实的文本 brief，而不是假媒体产物

## What Makes This Cool

真正让这次 demo 成立的，不是“我用了 agent”。

真正的“哇”点是：

- 它像一个真的创作导演流程，而不是一次性问答
- 每个节点都能落出像专业工作台一样的结构化文本产物
- 前一个节点的结果会真的进入下一个节点，而不是前端假装串起来
- 即使暂时没有真图片和真音频，这条链路仍然能完整跑通，并留下可供后续媒体生成消费的 brief

换句话说，这次 demo 卖的不是多 agent 人设，而是**可依赖的五段创作流水线**。

## Constraints

- 本期目标是 `Hackathon / 演示`，优先可演示性和稳定性，不追求通用框架抽象
- 前端节点展示已经基本够用，本期重点在后端流程语义和节点产物质量
- 当前已有统一文本生成接口，但只支持“传 prompt，拿文本”
- 当前没有原生 schema / JSON 输出保障
- 仍保留现有五节点：
  - `source_analysis`
  - `lyric_plan`
  - `composition_brief`
  - `cover_direction`
  - `audio_render`
- `cover_direction` 本期不生成真实图片
- `audio_render` 本期不生成真实音频
- 节点失败时允许自动重试 1 到 2 次，仍失败则停住
- 重试使用同一个 prompt，不做“带错误原因二次修正”
- 产物质量锚点是 `歌词结构` 节点

## Premises

1. 这次 Hackathon 版本的核心，不是通用 multi-agent 框架，而是线性、可恢复、结构化产出的文本工作流引擎。 — agree
2. `cover_direction` 和 `audio_render` 不应继续伪装成已生成图片和已生成音频；它们本期应是真实的文本 brief 节点。 — agree
3. 这次不引入通用 DAG/插件系统；继续保留五节点线性任务模型，但让每个节点具备独立 prompt、schema、重试和 artifact 持久化。 — agree

## Approaches Considered

### Approach A: 最小替换版

Summary:
只把前三个文本节点替换成真实文本 API，后两个节点继续保留本地 mock。

Effort: Medium
Risk: Low

Pros:
- 改动最少
- 最快可跑
- 对现有前后端冲击小

Cons:
- 后半段一眼能看出是假链路
- 观众很难相信“五个节点真串起来”
- 之后还要再重做完成态

Reuses:
- 现有 `orchestrator.py`
- 现有 `providers.py`
- 现有 `generation_tasks` 任务模型

### Approach B: 线性文本工作流 + 严格 schema + 真实 brief 完成态

Summary:
五个节点都保留，但全部变成真实文本节点。每个节点独立 prompt，模型必须在固定标记中返回 JSON；后端负责抽取、schema 校验、同 prompt 重试 1 到 2 次。`cover_direction` 输出视觉 brief，`audio_render` 输出音频导演说明。

Effort: Medium-Large
Risk: Low-Medium

Pros:
- 最符合 demo 目标
- 五个节点都是真节点
- 串行依赖关系真实成立
- 后续接图像和音频生成时，brief 可以直接复用

Cons:
- 需要设计 5 份 prompt 和 5 份 schema
- 需要补抽取/校验/重试层
- 对节点 artifact 质量要求更高

Reuses:
- 现有 `generation_tasks` 与 worker
- 现有前端节点展示
- 现有线性 orchestrator 思路

### Approach C: 通用 agent 编排版

Summary:
引入显式 agent registry、节点执行器、上下文交接抽象，把五个节点包装成通用 agent flow。

Effort: Large
Risk: Medium-High

Pros:
- 框架感更强
- 后续扩展更多节点更顺
- 更像“agent 平台”

Cons:
- 对这次 demo 明显过重
- 时间会花在抽象而不是产物质量
- 更难调试，失败路径更复杂

Reuses:
- 现有 worker 和任务存储
- 很少能直接复用现有 provider 逻辑

## Recommended Approach

选择 **Approach B: 线性文本工作流 + 严格 schema + 真实 brief 完成态**。

原因很直接：

- 你要演示的是“这条创作链路真的会一步一步跑”
- 不是“我搭了个 agent 框架”
- 也不是“前 3 步真，后 2 步假”

这条路径刚好把演示价值压在最该亮的地方：

- 五节点完整跑通
- 每步有清晰产物
- 下游依赖上游 artifact
- 失败可停住、可重试

## Workflow Model

### Stage order

保留当前线性顺序：

1. `source_analysis`
2. `lyric_plan`
3. `composition_brief`
4. `cover_direction`
5. `audio_render`

### Runtime contract

每个节点统一遵守以下契约：

- 输入：
  - 原始 `task.input`
  - 前置阶段 artifact（按节点需要注入）
- 执行：
  - 构造当前节点 prompt
  - 调统一文本接口
  - 从固定标记中抽取 JSON
  - 用本地 schema 校验
- 输出：
  - 校验通过的结构化 artifact
- 失败：
  - 同 prompt 自动重试 1 到 2 次
  - 仍失败则写入 error 并停在当前节点

### Fixed marker output protocol

因为当前文本接口没有原生结构化输出保障，所以每个节点统一要求模型按如下协议返回：

```text
<WORKFLOW_JSON>
{ ...valid json... }
</WORKFLOW_JSON>
```

后端只认这对固定标记中的 JSON 内容。

处理顺序：

1. 查找开始/结束标记
2. 抽取中间文本
3. `json.loads`
4. schema 校验
5. 成功则落盘，失败则重试

这次不允许“自然语言结果也算成功”。

## Stage Artifacts

### 1. `source_analysis`

Purpose:
把题材输入整理成后续歌词创作可消费的叙事与情绪基础。

Required fields:

- `summary`
- `coreConflict`
- `themes`
- `emotionArc`
- `motifs`
- `audienceLens`
- `lyricFocus`

Notes:
- 它不是影评摘要
- 必须服务后续歌词结构节点

### 2. `lyric_plan`

Purpose:
这是整条链路的质量锚点。它既要给出创作策划，也要给出半成品歌词抓手。

Required fields:

- `concept`
- `narrativePOV`
- `sections`
- `hook`
- `keyLines`
- `chorusDraft`
- `languageStyle`
- `forComposition`

Notes:
- 以创作策划为主
- 但必须包含关键句和副歌候选
- 结果看起来要像“专业创作工作台产物”，不能像普通聊天回答

### 3. `composition_brief`

Purpose:
把歌词结构转成可供音乐制作使用的音乐 brief。

Required fields:

- `titleProposal`
- `tempo`
- `key`
- `timeSignature`
- `arrangement`
- `vocalDirection`
- `sectionDynamics`
- `mixMood`

Notes:
- 必须显式消费 `lyric_plan`
- 不能只给几个 BPM/调式参数了事

### 4. `cover_direction`

Purpose:
输出封面创意说明和后续生图可消费的视觉 brief。

Required fields:

- `coverTitle`
- `visualConcept`
- `composition`
- `palette`
- `subjectFocus`
- `negativeSpace`
- `renderPrompt`
- `avoid`

Notes:
- 本期不生成真实图片
- 不再输出假 `coverUrl`
- 这是一个真实的“视觉导演 brief”

### 5. `audio_render`

Purpose:
输出音频导演说明和后续音频生成可消费的音乐执行 brief。

Required fields:

- `versionTitle`
- `performanceDirection`
- `instrumentation`
- `chorusLift`
- `introDirection`
- `endingDirection`
- `productionNotes`
- `renderPrompt`

Notes:
- 本期不生成真实 `audioUrl`
- 不再伪造可播放音频
- 这是一个真实的“音频导演说明”

## Result Model

当前 `current_result` 不再假装代表“最终媒体资产”，而应代表“当前最值得展示的阶段结果摘要”。

建议：

- `title`
  - 优先来自 `composition_brief.titleProposal`
- `coverUrl`
  - 本期可为空
- `audioUrl`
  - 本期可为空
- `activeStyle`
  - 不再只是固定 `default`
  - 可从歌词结构或编曲 brief 派生出更接近创作风格的文本标签
- `currentHighlight`
  - 新增：当前阶段最关键的摘要句

这样前端顶部展示区仍然成立，但不再依赖假的媒体结果。

## Failure Model

### Node-level retry

每个节点统一策略：

- 第 1 次失败：记录失败原因到内存，立即同 prompt 重试
- 第 2 次失败：再次同 prompt 重试
- 第 3 次仍失败：任务停住，状态写为 `failed`

### Persisted error

失败时任务里至少保留：

- `stage`
- `message`
- `retryable`
- `attempts`

### Retry semantics

用户点击“重试”时：

- 保留失败点之前已成功的节点
- 清空当前失败节点及其后续节点
- 重新回到当前失败节点开始执行

## Prompt Design Rules

所有节点 prompt 必须遵守：

- 明确当前节点职责，不混写后续节点内容
- 明确消费哪些上游 artifact
- 明确输出字段说明
- 明确禁止多余解释
- 明确必须使用 `<WORKFLOW_JSON>...</WORKFLOW_JSON>` 包裹 JSON
- 明确中文产物风格要像“专业创作工作台文档”，不是聊天语气

统一要求：

- 语气：专业、简洁、创作导向
- 输出：中文
- 不写寒暄
- 不写“当然”“以下是”
- 不写 markdown

## Implementation Shape

建议后端形状：

- `providers.py`
  - 不再是本地 mock provider 集合
  - 改成节点 prompt builder + 文本接口调用封装
- `orchestrator.py`
  - 继续保留显式线性流程
  - 新增固定标记抽取、schema 校验、节点重试
- `worker.py`
  - 继续负责后台消费 queued 任务
- `db.py`
  - 继续保存阶段 artifact、错误、任务状态

本期**不建议**额外抽象出通用 agent framework。

## Success Criteria

这次 demo 的完成标准是：

- 输入一个电影题材后，五个节点都能稳定跑完
- 每个节点结果都是结构化文本 artifact
- `lyric_plan` 明显像专业创作工作台产物
- `cover_direction` 和 `audio_render` 是真实 brief，不是假媒体产物
- 任一节点解析失败时会自动重试，并能在失败后稳定停住
- 点击重试后，能从失败节点继续，不污染前面已成功结果

## Distribution Plan

这次 deliverable 仍然是现有 web workspace：

- 用户入口：本地/部署后的网页工作台
- 分发方式：现有仓库与部署链路
- CI/CD：沿用现有 web 服务发布方式

本期不新增二进制、SDK 或外部分发形态。

## Open Questions

- 后续接入真图片/真音频时，是覆盖 `cover_direction` / `audio_render`，还是新增下游媒体执行节点

6. 补后端测试：

   - 失败停住
   - 从失败节点重试
