## Problem Statement

Build a visual interface for automatic song creation where the user can input a movie or TV show title, then watch the system turn that source material into a complete music release package.

The core product is not just "generate a song." It is a visible creative workflow that shows what each stage is doing: story extraction, emotion analysis, lyric planning, composition direction, cover creation, and final release packaging. The first closed-loop demo should end with a playable song artifact plus supporting creative materials.

## What Makes This Cool

The "whoa" moment is not merely that AI outputs music. It is that the product turns a known story world into something that feels like a real soundtrack single, while exposing the reasoning chain that got there.

For music-production enthusiasts, the delight comes from three things happening together:

1. The source topic is legible and recognizable.
2. The intermediate creative decisions are visible rather than hidden in a black box.
3. The final output looks like a real release, not a pile of disconnected AI assets.

## Constraints

- The project is being framed as a hackathon/demo build, so the first version must optimize for a complete, compelling walkthrough rather than a broad platform.
- The first release should focus on a single closed loop:
  `movie/TV title -> plot and emotion analysis -> lyrics -> composition brief -> cover -> release page`
- The product must eventually generate the actual song, not stop at analysis.
- The UI must make each stage understandable to a non-technical creative user.
- The target early audience is music-production enthusiasts, not general casual consumers.
- The interface should leave room for future style branches from the same song concept.

## Premises

1. Core value = visible creative derivation chain plus actual song generation, not analysis-only.
2. The right first milestone is one narrow but complete flow around film/TV source material, not a general-purpose music workbench.
3. Early adopters will care that they can inspect process and compare outputs, not just click once and get a file.
4. The release-page framing is the most demo-effective way to package the result for a hackathon audience.
5. Style-switching is a major long-term differentiator, but should land after the first end-to-end loop works.

## Approaches Considered

### Approach A: Release-Page Closed Loop

Summary:
Build one polished path from source title to final "single release" page. The system visibly steps through analysis, lyric generation, composition notes, cover generation, and song output, then presents everything as a cohesive release artifact.

Effort: Medium
Risk: Low

Pros:
- Highest demo quality for the least scope.
- Best fit for the user's stated minimum viable loop.
- Makes the product feel complete even if generation quality is uneven.
- Easy to narrate in a live demo or short video.

Cons:
- Users can inspect process, but not deeply manipulate it yet.
- The workflow is guided, not fully exploratory.
- Style branching may need to be shown as a preview or teaser rather than a fully developed subsystem.

Reuses:
- Existing LLM orchestration patterns
- Existing music-generation APIs
- Existing image-generation APIs
- Conventional stepper / pipeline UI patterns

### Approach B: Creative Workbench

Summary:
Make the workflow itself the main interface: a visible chain of nodes for analysis, lyrics, composition, cover, and audio generation, each with intermediate state and rerun controls.

Effort: Large
Risk: Medium

Pros:
- Most faithful to the long-term vision.
- Strongest articulation of "each node clearly shows what it is doing."
- Natural base for later branching, version compare, and manual editing.

Cons:
- Higher UI and state-management complexity.
- Easier to ship half-built and underwhelming in a hackathon timeframe.
- Risk of spending too much time on workflow chrome instead of the core "movie to release" magic.

Reuses:
- Visual workflow canvas libraries
- Log/event panel patterns
- Re-runnable job execution patterns

### Approach C: Branching Adaptation Studio

Summary:
Generate one base song package from the source title, then make version-switching the hero feature by creating alternate style branches from the same underlying song thesis.

Effort: Medium to Large
Risk: Medium

Pros:
- Strong differentiation for music enthusiasts.
- Makes the creative reasoning feel musical, not just textual.
- Great for side-by-side comparison clips and social sharing.

Cons:
- Depends on a solid base-song pipeline first.
- Could feel like "same thing with different prompts" if the analysis chain is weak.
- Harder to make legible in one weekend than a single polished release path.

Reuses:
- Base release generation pipeline from Approach A
- Compare view patterns
- Variant-generation and parameter-locking patterns

## Recommended Approach

Choose **Approach A: Release-Page Closed Loop**.

This is the smallest boilable lake that still proves the thesis. It preserves the essential product identity:

- visible reasoning chain
- actual song output
- complete release packaging

It also creates the right migration path:

1. Ship a strong, narratable end-to-end demo.
2. Add per-step controls and rerun affordances.
3. Add style branches from the same song concept.
4. Expand from guided flow into a real creative workbench.

## Visual Direction

The interface should look better than a generic AI workflow dashboard. The right direction is a **professional music creation workspace with film-scoring context**, not a player app and not a node-editor toy.

- **Production-workspace framing**: the page should feel like a serious music-making tool where source references, emotional arcs, arrangement calls, and output branches coexist.
- **Reference context stays visible**: source material, motifs, and emotional context should stay visible rather than disappearing after input.
- **Decision runway in the center**: the creative chain should read like a sequence of production judgments, not a technical pipeline log.
- **Inspector on the right**: style branches and branch-specific notes should feel like alternate production versions under review.
- **Release artifact as payoff, not homepage identity**: the final song package is still important, but the main identity is music creation with transparent reasoning.

Visual thesis:

- Warm studio neutrals rather than flat grayscale SaaS.
- Feels closer to a modern scoring / production console than a marketing page.
- Soft but disciplined surfaces, not hard enterprise widgets and not decorative concept art.
- Enough visual identity to feel premium, but the dominant impression should be control and clarity.
- Style branches shown as alternate production versions, not mere feature toggles.

The goal is for someone to think:
"This looks like a serious music creation workspace" before they even parse the workflow.

### Chinese Interface Language

Chinese copy should lean **professional music-production language**, not dramatic movie-poster language.

That means:

- Prefer `当前版本`, `编曲设定`, `歌词结构`, `情绪走向`, `风格分支`, `生成中`
- Avoid over-theatrical labels like `命运抉择`, `灵感风暴`, `终极史诗版`
- Buttons should read like tool actions:
  - `生成当前版本`
  - `展开查看`
  - `重新生成这一段`
  - `切换到民谣版`
  - `补充剧情简介`
- Section headings should orient the user quickly:
  - `当前歌曲`
  - `创作流程`
  - `题材参考`
  - `分支版本`

The language should make the product feel trustworthy to music enthusiasts who care about structure and production decisions.

### Anti-Slop Layout Rule

The core workflow area must use an **inspector layout**, not stacked cards.

Structure:

- Left column: stage list rows
- Right column: active stage detail

The stage list should behave like a production queue or arrangement checklist:

- fixed row rhythm
- short title
- one-line summary
- state chip
- optional retry / expand action

The detail panel should show:

- what source input this step used
- what judgment it made
- what artifact it produced
- what can be regenerated

Cards are allowed only where the card is the interaction itself:

- current song result module
- cover preview
- branch version tile

Cards must not be used as the default structure for the workflow body.

## UX Outline

## Information Architecture

### Screen Hierarchy

The product should use a **result-first, explanation-second** hierarchy.

This is a deliberate choice: the first screen should hook the user with the current generated song package, then immediately reveal the creative chain that produced it. That means the product reads less like a blank workflow tool and more like a soundtrack-director desk with a live result pinned to the top.

Priority order:

1. **Current Song Result**
   What the user notices first: song title, cover, playback module, active style version.
2. **Creative Derivation Chain**
   What the user notices second: story extraction, emotion arc, lyric plan, composition brief, cover direction, render step.
3. **Reference Context**
   What the user notices third: movie/TV title, source summary, motifs, emotional thesis.

### Layout Structure

Desktop should feel like one composed director surface:

```text
+----------------------------------------------------------------------------------+
| Hero Result: cover + track title + playback + active style branch               |
+--------------------------------------+-------------------------------------------+
| Creative Chain / Decision Runway     | Branch Inspector / Compare Notes          |
| analysis -> lyric plan -> arrange -> | active version / alternate directions     |
| cover direction -> render            | what changed in this branch               |
+--------------------------------------+-------------------------------------------+
| Reference Wall: source title + story summary + mood arc + motifs                |
+----------------------------------------------------------------------------------+
```

### Section Jobs

- **Hero Result**
  One job: prove there is a real song artifact worth inspecting.

- **Creative Chain**
  One job: explain how the product got there.

- **Branch Inspector**
  One job: show that style variation is intentional, not random rerolling.

- **Reference Wall**
  One job: anchor the song back to recognizable source material.

### Navigation Logic

This should be a **single-screen workspace**, not a multi-page app for v1.

- No top nav with multiple destinations.
- No separate "results page" detached from the workflow.
- The user should scroll through one coherent workspace from result to reasoning to source context.

### Default Disclosure Model

The creative chain should default to a **collapsed list of stages**.

That means:

- Each stage row is closed by default.
- Each row still shows one plain-language summary line.
- Each row shows an at-a-glance state:
  - not started
  - generating
  - ready
  - failed
- Selecting a row opens its detail content inline or in the adjacent inspector.

This keeps the page visually controlled while preserving inspectability.

Important guardrail:
The collapsed state must not read like a developer log. Every stage row must use creative, audience-readable language. Example summaries:

- `剧情提炼：识别出反抗命运与牺牲两条主线`
- `歌词规划：副歌聚焦不认命，主歌保留脆弱感`
- `作曲设定：92 BPM，D 小调，副歌抬升，鼓点更重`

If a collapsed row cannot communicate value in one line, the stage itself is underspecified.

### Primary User Flow

1. User enters a movie or TV show title.
2. System lands the user on a hero result area with the current song package front and center.
3. Immediately below, the workflow panel reveals each stage in sequence:
   - Content Analysis
   - Emotion Curve
   - Lyric Plan
   - Composition Brief
   - Cover Direction
   - Song Render
4. A lower reference section keeps the source title, themes, character tension, and mood arc visible.
5. Each stage displays:
   - What input it used
   - What it decided
   - What artifact it produced
6. The workspace always keeps the result package visible enough that the user understands what branch is currently active.
7. The result area becomes a release-style artifact with:
   - title
   - cover
   - playable song
   - lyrics
   - composition metadata
   - one-click style branch teaser

### Key UI Principle

The center of gravity should be a **visible derivation chain**, not a blank prompt box. The product should feel like watching a producer's board fill in, not like talking to a chatbot.

### Stage Design

- **Source Card**
  Shows the entered title, fetched/derived story snapshot, and a short note about the intended musical framing.

- **Analysis Stage**
  Extracts plot themes, emotional arc, conflict, symbolic motifs.

- **Lyric Planning Stage**
  Converts story/emotion into song structure before drafting lyrics.

- **Composition Brief Stage**
  Outputs BPM, key, arrangement direction, instrumentation, vocal stance, and section dynamics.

- **Cover Direction Stage**
  Produces art guidance and one selected cover image.

- **Song Render Stage**
  Calls the actual music-generation system and returns a playable track.

- **Release Page**
  Packages everything into one coherent final artifact.

## Responsive & Accessibility

### Responsive Scope

Version 1 is **desktop-first**.

Decision:
- Do not build a full mobile creation workflow in this phase.

Minimum responsive requirement:
- Optimize for desktop and laptop widths first.
- Treat small-screen mobile as unsupported for the full workspace.
- On narrow screens, do not squeeze the desktop layout into a broken long column.
- Instead, show a lightweight fallback screen that explains:
  - this workspace is designed for desktop
  - the product turns film/TV titles into songs with visible creative steps
  - a desktop device is recommended for the full creation flow

Supported viewport targets for v1:
- **Desktop:** 1440px and above as the primary target
- **Laptop:** 1280px and above must still feel intentional
- **Small laptop:** 1024px and above must remain usable with tighter spacing

### Desktop Layout Behavior

- The hero result stays at the top.
- The workflow body uses a left-list / right-inspector layout.
- The reference section sits below the workflow, not inside a side drawer.
- Branch inspector remains visible on desktop without hidden hover-only controls.

### Accessibility Requirements

Even as a desktop-first build, accessibility is required.

- Keyboard navigation:
  - every stage row must be reachable by tab
  - expanding a stage must work without a mouse
  - branch switching must be keyboard-operable
- Focus behavior:
  - a clearly visible focus ring is required
  - when a stage opens, focus should move predictably to the detail region or remain on the trigger consistently
- Screen reader support:
  - use clear section landmarks for `当前歌曲`, `创作流程`, `题材参考`, `分支版本`
  - stage states such as `生成中`, `已完成`, `失败` must be announced in accessible text
- Touch / click targets:
  - even on desktop, interactive controls should target at least 44px effective hit area
- Contrast:
  - text and state chips must meet readable contrast without relying on faint decorative styling
- Motion:
  - progressive generation transitions should support reduced-motion preferences

## Success Criteria

The demo is successful if a first-time viewer can understand the product in under 30 seconds and say:

- "I see how the movie became the song."
- "I can tell what each stage contributed."
- "This feels like a real single release, not just some AI text."
- "I want to try another movie or branch this into another style."

Operational success criteria:

- All six stages produce visible artifacts.
- A playable audio artifact appears on the release page.
- The release page can be screenshotted or demoed as a standalone shareable result.

## Interaction State Coverage

The product should use **progressive generation**, not one blocking page-level loading state.

That means the workspace appears immediately, then each stage advances independently. Users should be able to see completed work as soon as it exists, rather than waiting for the entire pipeline to finish.

### State Table

| Feature | Loading | Empty | Error | Success | Partial |
|--------|---------|-------|-------|---------|---------|
| 题材输入区 | 输入后按钮进入进行中状态，展示“正在分析题材” | 首次进入时显示示例片名和一句引导，如“输入一个电影或剧名，系统会把它拆成一首歌” | 输入无法识别时提示“没找到可用题材信息”，并提供“改用一句剧情描述继续” | 成功后显示题材标题、来源摘要、情绪主线 | 只识别到标题未识别到剧情时，显示标题并提示补一段简介 |
| 当前歌曲成品区 | 先显示占位封面、占位标题、禁用播放器，并显示“正在形成当前版本” | 初次未生成前显示“这里会出现你的当前版本歌曲”以及一个示例截图式占位 | 音频生成失败时保留其余结果，播放器位显示“歌曲生成失败，可重新生成当前版本” | 显示封面、标题、可播放音频、当前风格标签 | 歌词/封面已完成但音频仍在生成时，显示“歌词与封面已准备好，歌曲还在生成” |
| 创作链步骤列表 | 各步骤逐步从“生成中”进入“已完成”，当前步骤有显著状态 | 尚未开始的步骤显示一句结果预期，如“这里会出现歌词规划摘要” | 单步骤失败时显示失败标签、失败原因一句话、单独重试入口 | 每行显示一句人话摘要，点开可看详细内容 | 某些步骤成功、后续步骤失败时，已完成步骤保持可查看，不被回退 |
| 分支检查区 | 在主版本完成前显示“分支稍后可用” | 初次生成前显示“完成主版本后可派生民谣版、摇滚版等” | 分支生成失败时只影响该分支，不影响当前主版本试听 | 显示当前分支、候选分支、每个分支的一句差异说明 | 主版本成功但分支尚未生成时，显示可点击但带“准备中”状态 |
| 参考题材区 | 摘要与情绪线先于音频完成，可率先出现 | 无输入时显示一个热门题材示例和解释文案 | 题材摘要获取失败时，提示用户手动补剧情，不阻断后续歌词生成 | 显示片名、摘要、情绪线、视觉母题 | 只成功提取到部分信息时，缺失字段用“待补充”而不是整区消失 |

### State Behavior Rules

- Never blank the whole page during generation.
- Never hide completed work just because a later stage failed.
- Every error state must preserve the user's existing progress.
- Every empty state must teach the user what this area will eventually become.
- Every loading state should describe the current creative task in human language, not technical terms.

## User Journey & Emotional Arc

The first-time experience should default to a **finished seeded example**, not an empty workspace.

That means a new visitor lands on a completed, recognizable soundtrack package for a known movie or show. Only after they understand the result and the visible derivation chain should the interface pull attention toward "try your own title."

### Why

This reduces intimidation and teaches the product through observation rather than instructions. It also gives the user an emotional sequence:

1. curiosity: "What is this thing?"
2. comprehension: "Oh, it turns a known story into a song."
3. trust: "I can see how it made those decisions."
4. ambition: "I want to try my own title."

### Storyboard

|-----|-----------|------------|-----------------|
| 1 | Lands on page and sees a seeded example | Curious but not lost | Yes — a finished example is visible immediately |
| 2 | Scans cover, title, playback, and active style branch | Hooked by a real result | Yes — hero result is the first hierarchy layer |
| 3 | Opens or scans collapsed stage rows | Reassured that the output is explainable | Yes — each row has a one-line summary and state |
| 4 | Scrolls to source context and mood arc | Understands how the movie became the song | Yes — reference wall anchors the result back to the source |
| 5 | Clicks into own input flow | Ready to try, not intimidated | Partially — CTA behavior should be specified in implementation plan |

| 7 | Hears a playable result and compares branches | Rewarded, then curious to iterate | Yes — result area plus branch inspector support this |

### Time-Horizon Design

- **First 5 seconds**
  The user should understand there is already a real song artifact here, not an empty tool.

- **First 5 minutes**
  The user should understand how story, emotion, lyrics, arrangement, and result connect.

- **First successful session**
  The user should feel they directed a soundtrack outcome, not merely filled in a prompt box.

## Engineering Execution Plan

### Implementation Strategy

Version 1 should use a **separate frontend and backend architecture**.

Recommended split:

- frontend: dedicated web workspace application
- backend: dedicated `FastAPI + Python` service

Why this is the accepted direction:

- The user explicitly wants frontend/backend separation.
- The backend generation pipeline benefits from Python ecosystem flexibility for provider integrations.
- It keeps the task API boundary explicit and reviewable.

Version 1 should use a **task-based generation pipeline**, not a single blocking request.

That means:

- The client creates a generation task when the user submits a title or title + synopsis.
- The server returns a task identifier immediately.
- The client then reads task state progressively and renders each stage as it becomes available.
- The final song package is assembled from staged artifacts rather than a single synchronous response.

Why this is the right v1 architecture:

- It matches the product promise of visible progressive generation.
- It allows partial success without losing finished work.
- It makes retries and branch generation possible without reloading the whole page.
- It keeps the mental model explicit: one workspace session maps to one generation task.

### v1 State Model

Version 1 should use a **linear stage state model**.

Stages:

1. source_analysis
2. lyric_plan
3. composition_brief
4. cover_direction
5. audio_render
6. completed

Rules:

- Only one active stage at a time.
- Each stage can be:
  - not_started
  - running
  - succeeded
  - failed
- Completed stage outputs remain visible even if a later stage fails.
- Retry in v1 should be modeled as re-running a single failed stage in the same linear task, not as a parallel branch graph.

Explicit v1 tradeoff:

- This keeps the implementation smaller and easier to ship.
- It does **not** attempt to model full branch lineage or concurrent alternate versions.

Future-compatible guardrail:

- Store stage outputs as structured artifacts by stage name.
- Do not hardcode UI assumptions that there can never be multiple versions later.

### Persistence Model

Version 1 should persist each generation session as **one durable generation task record**.

Recommended shape:

- `generation_task.id`
- `generation_task.status`
- `generation_task.current_stage`
- `generation_task.input`
- `generation_task.stage_artifacts`
- `generation_task.error`
- `generation_task.created_at`
- `generation_task.updated_at`

Where:

- `input` stores the submitted title, optional synopsis, and any user-selected mode
- `stage_artifacts` stores structured outputs by stage name
- `error` stores the current user-visible failure state, if any

Why this is the right v1 persistence model:

- Durable enough for retries, refresh, and partial success
- Smaller than a fully normalized workflow schema
- Explicit enough to support testing and UI rendering without hidden state

Out of scope for v1:

- separate stage table
- branch lineage table
- fully normalized artifact graph

### Client Update Model

Version 1 should use **HTTP polling** to read task progress.

Recommended pattern:

- `POST /generation-tasks` creates the task and returns the task id immediately
- `GET /generation-tasks/:id` returns the latest task snapshot
- the client polls on a short interval while task status is active
- polling stops automatically when the task reaches `completed` or `failed`

Why this is the right v1 choice:

- It is the most boring and reversible implementation.
- It is enough to deliver progressive generation UX.
- It avoids the operational and reconnection complexity of WebSockets or SSE in a project that does not yet have infrastructure.

Future-compatible guardrail:

- Keep the task response shape stable so polling can later be replaced by push updates without changing the workspace rendering model.

### API Contract

Version 1 should expose a **full task snapshot contract**.

That means every `GET /generation-tasks/:id` response returns the complete current workspace state needed by the client, not a sparse patch that the client must reconstruct.

Recommended response shape:

```json
{
  "id": "task_123",
  "status": "running",
  "currentStage": "composition_brief",
  "input": {
    "title": "哪吒",
    "synopsis": "..."
  },
  "stages": {
    "source_analysis": { "status": "succeeded", "artifact": {} },
    "lyric_plan": { "status": "succeeded", "artifact": {} },
    "composition_brief": { "status": "running", "artifact": null },
    "cover_direction": { "status": "not_started", "artifact": null },
    "audio_render": { "status": "not_started", "artifact": null }
  },
  "currentResult": {
    "title": null,
    "coverUrl": null,
    "audioUrl": null,
    "activeStyle": "default"
  },
  "error": null
}
```

Why this is the right v1 contract:

- The client can render directly from one explicit object.
- Tests can assert contract snapshots without hidden recomposition logic.
- Partial success, error states, and future retries all become easier to reason about.

### Server Orchestration

Version 1 should use **one generation orchestrator** that runs the linear stages in order.

Recommended responsibility split:

- route handler:
  - validate request
  - create task record
  - trigger orchestrator
  - return task id
- orchestrator:
  - load task
  - run each stage in order
  - persist stage artifacts after each success
  - mark failure explicitly when a stage fails
- provider adapters:
  - source analysis provider
  - lyric planning provider
  - composition brief provider
  - cover generation provider
  - audio generation provider

Why this is the right v1 shape:

- The route handler stays thin.
- The orchestration logic is explicit and testable in one place.
- Provider-specific logic can evolve independently without introducing a full worker platform.

### Backend Runtime Model

Version 1 backend should be split into:

- **FastAPI API service**
  - request validation
  - task creation
  - task snapshot reads
  - retry endpoints
- **Dedicated worker process**
  - claims queued tasks
  - runs the generation orchestrator
  - persists stage artifacts and failure state

Why this is the right v1 backend model:

- API request handling stays fast and stateless.
- Long-running generation work does not depend on API process lifetime.
- It avoids premature queue-platform complexity while still being operationally safer than in-process background tasks.

Recommended v1 queue model:

- use the durable `generation_task` record itself as the work queue source of truth
- worker polls for tasks in `queued` or retryable states
- worker marks tasks `running`, advances stages, and writes terminal state

Not in scope for v1:

- Celery / Redis / distributed queue platform
- horizontally scaled worker coordination beyond basic task claiming

### Provider Timeout and Retry Policy

Version 1 should use a **stage-level timeout and retry policy** shared across providers.

Required policy shape:

- every external provider call has an explicit timeout
- every stage defines a bounded retry count
- retries use backoff, not hot-loop retries
- when retries are exhausted, the task snapshot must expose a user-visible failed state

Recommended v1 defaults:

- source_analysis: short timeout, low retry count
- lyric_plan: short timeout, low retry count
- composition_brief: short timeout, low retry count
- cover_direction: medium timeout, low retry count
- audio_render: longest timeout, low retry count

Why this is the right v1 performance/stability policy:

- Long-running provider calls cannot silently stall the worker forever.
- Retry behavior stays predictable and testable.
- User-visible status remains aligned with backend truth.

Not in scope for v1:

- queue-backed distributed workers
- separate service object per stage with independent lifecycle management
- generic workflow engine abstraction

### Frontend State Management

Version 1 should split frontend state into two layers:

- **server state:** managed by `TanStack Query`
- **local workspace UI state:** managed by a page-level `useReducer`

Recommended local reducer responsibilities:

- seeded example vs user workspace mode
- selected workflow row
- expanded/collapsed state
- retry intent UI state
- local presentation-only flags

Recommended server state responsibilities:

- create task mutation
- task polling query
- refresh after retry
- request lifecycle and cache invalidation

Why this is the right v1 split:

- Server truth stays in one place.
- Workspace UI state remains explicit and local to the page.
- It avoids both prop-drilling chaos and premature global store complexity.

### Provider Adapter Contract

Each generation stage should define a **standard provider interface** and a **standard artifact shape**.

That means:

- the orchestrator calls a stage adapter, not raw provider-specific response shapes
- each adapter maps provider output into the stage's canonical artifact format
- provider-specific fields do not leak into the workspace rendering contract

Recommended v1 pattern:

- `runSourceAnalysis(input) -> SourceAnalysisArtifact`
- `runLyricPlan(input, sourceAnalysis) -> LyricPlanArtifact`
- `runCompositionBrief(input, lyricPlan) -> CompositionBriefArtifact`
- `runCoverDirection(input, compositionBrief) -> CoverArtifact`
- `runAudioRender(input, compositionBrief, lyricPlan) -> AudioArtifact`

Why this is the right v1 quality bar:

- The orchestrator stays DRY and readable.
- Swapping providers later is localized to adapter code.
- Tests can assert canonical artifacts rather than vendor-specific payloads.

Not in scope for v1:

- global plugin registry
- dynamic provider loading
- user-configurable provider marketplace

### Test Strategy

Version 1 should use **fake/stub providers in automated tests** and reserve real third-party providers for separate smoke verification.

Recommended testing split:

- unit tests:
  - stage adapters map provider output into canonical artifacts
  - orchestrator state transitions
  - snapshot serialization
- integration tests:
  - `POST /generation-tasks`
  - `GET /generation-tasks/:id`
  - persistence of stage artifacts and failure state
- E2E tests:
  - seeded example to user workspace transition
  - submit title and watch progressive generation
  - failed later stage preserves earlier artifacts
- smoke checks outside normal CI:
  - one source analysis provider call
  - one cover provider call
  - one audio provider call

Why this is the right v1 test strategy:

- CI stays deterministic and fast.
- The system is tested against canonical artifacts rather than unstable vendor responses.
- Real provider connectivity is still verified without making the whole suite flaky.
