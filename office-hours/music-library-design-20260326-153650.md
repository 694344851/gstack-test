## Problem Statement

The current product is centered on a single active generation task. Once a song is generated, the user can inspect the current result, but there is no dedicated place to return to older songs, replay them, or treat them as an accumulating body of work.

The new problem is not "add history." It is: create a **My Library** area that turns one-off generations into an ongoing creative archive.

## What Makes This Cool

The exciting version is not a plain history list. It is a **creator portfolio inside the workbench**:

- each work has a cover, title, source, and time
- the library feels like a body of authored work, not a log table
- opening a work does not just replay audio; it reopens the creative reasoning that produced it
- over time, works can be organized into series by movie, style, and time

The "whoa" moment is:
"I am not generating disposable songs. I am building a catalog."

## Constraints

- This should become the **second main area** of the product, alongside the current active workspace.
- Version 1 should stay narrow: the first goal is a **card-based library view**, not a full archive platform.
- The first visible card fields are:
  - title
  - cover
  - source
  - time
- The user explicitly wants the detail value to be:
  - "see the original creative process for that work"
- Future grouping by movie, style, and time should be anticipated, but not required for v1.

## Premises

1. `我的作品库` is a primary workbench area, not a hidden history page.
2. V1 should first prove that generated songs persist and feel collectible.
3. The homepage of the library should behave like a creator portfolio, not like a table of jobs.
4. The detail view should eventually act as a historical task replay surface, not only a playback page.
5. Automatic series organization is a strong differentiator, but belongs after the base library exists.

## Approaches Considered

### Approach A: Card-Based Library

Summary:
Add a left-nav `我的作品库` entry and show a card grid for previously generated songs. Each card emphasizes cover, title, source, and time.

Effort: Medium
Risk: Low

Pros:
- Cleanest first expansion from the current product
- Immediately solves the "where do old songs go?" problem
- Makes the product feel persistent rather than disposable
- Uses metadata the system already has or can easily persist

Cons:
- Detail depth is still deferred
- Grouping and series logic are only implied, not yet realized
- Without a strong card design, it can regress into a bland history grid

Reuses:
- existing `generation_task` persistence
- existing title / cover / source / timestamps
- existing left-nav workbench framing

### Approach B: Library + Historical Replay

Summary:
Build the card library and let the user click into a work-specific detail page that replays the full creative flow for that song.

Effort: Large
Risk: Medium

Pros:
- Best fit with the user's stated value for detail pages
- Strong continuity with the current workbench
- Turns every song into a durable creative artifact

Cons:
- Requires a stronger distinction between "active task" and "archived task"
- More UI and data-model work than v1 needs
- Harder to keep narrow if implemented immediately

Reuses:
- current workflow stage rendering
- current song result module
- current inspector patterns

### Approach C: Series-First Portfolio

Summary:
Make the library page immediately group works into series by movie, style, or time instead of starting with a flat card grid.

Effort: Medium to Large
Risk: Medium

Pros:
- Most differentiated long-term vision
- Best alignment with "creator portfolio" framing
- Makes the archive feel editorial and intentional

Cons:
- Too early if the library is still small
- Requires grouping logic before the product has enough volume to justify it
- Risks complexity without first proving basic revisit behavior

Reuses:
- source title
- style metadata
- creation timestamps

## Recommended Approach

Choose **Approach A: Card-Based Library**.

This is the right first lake to boil because it changes the product category immediately:

- from single-task generator
- to persistent creation environment

It also creates the right migration path:

1. Add `我的作品库` as the second main nav area.
2. Show a clean grid of works with cover, title, source, and time.
3. Make each card clickable.
4. Turn the click target into a historical creative replay view.
5. Later add automatic series organization by movie, style, and time.

## Engineering Direction

### Storage Rule

Version 1 should **not** create a separate `library_items` table.

Instead, `我的作品库` should derive its list from the existing durable `generation_tasks` storage.

Why this is the right v1 rule:

- avoids duplicate persistence
- avoids sync drift between "task" and "work"
- keeps the diff minimal
- preserves a future path where archived work detail can open directly from the original task record

This means the library is defined as:

- a filtered, ordered projection of `generation_tasks`
- serialized through a dedicated library-list response shape
- backed by existing fields already persisted in the task row

### Inclusion Rule

Version 1 library entries should only include tasks with:

- `status = completed`

Rejected for v1:

- showing failed tasks in the same portfolio view
- showing in-progress tasks in the same portfolio view

Rationale:

- the library is positioned as a creator portfolio, not a raw task history
- completed-only keeps card density visually stable
- it avoids shipping ambiguous half-state cards before the product defines archive semantics for partial work

### API Shape Rule

The library index should **not** return full task snapshots.

Version 1 should expose a dedicated **library card DTO** for the card wall.

Why:

- the card wall consumes "work identity" rather than workflow internals
- it prevents the list page from coupling itself to full task execution shape
- it keeps future archived-detail and replay endpoints free to evolve independently

This means:

- list API returns a compact, card-focused response
- task detail API remains the source of truth for full workflow replay

### Version 1 List Endpoint

Recommended endpoint:

- `GET /library/works`

Recommended behavior:

- returns only records derived from `generation_tasks` where `status = completed`
- sorts by `created_at DESC`
- returns a dedicated library-card payload

### Version 1 Library Card DTO

```json
{
  "items": [
    {
      "id": "task_xxx",
      "title": "流浪地球·逆光版",
      "coverUrl": "data:image/svg+xml,...",
      "sourceTitle": "流浪地球",
      "createdAt": "2026-03-26T07:07:27.438285+00:00",
      "activeStyle": "默认版本",
      "hasAudio": true
    }
  ]
}
```

Field notes:

- `id`: original task id, reused later for archived replay
- `title`: from `current_result.title`
- `coverUrl`: from `current_result.coverUrl`
- `sourceTitle`: from `input.title`
- `createdAt`: from `created_at`
- `activeStyle`: from `current_result.activeStyle`
- `hasAudio`: derived from whether `current_result.audioUrl` is present

### What Already Exists

- existing durable storage in `generation_tasks`
- existing task result fields:
  - `current_result.title`
  - `current_result.coverUrl`
  - `current_result.audioUrl`
  - `current_result.activeStyle`
- existing task input field:
  - `input.title`
- existing timestamps:
  - `created_at`

### Architecture Notes

The minimum v1 backend change should look like this:

```text
frontend library page
        |
        v
GET /library/works
        |
        v
query generation_tasks
  WHERE status = completed
  ORDER BY created_at DESC
        |
        v
map rows -> LibraryCardDTO
        |
        v
return { items: [...] }
```

Implementation guidance:

- add one backend read path for listing works
- do not mutate task rows to "promote" them into library entries
- do not create a new persistence model
- keep archived detail on the existing `GET /generation-tasks/{id}` path for later

### Required Tests

- unit/integration: list endpoint returns only completed tasks
- unit/integration: list endpoint sorts by newest first
- unit/integration: DTO mapping uses the correct source fields
- unit/integration: `hasAudio` flips false when `audioUrl` is null
- integration: empty database returns `{ items: [] }`
- regression: failed and queued tasks do not leak into the library list

## Failure Modes

| Codepath | Realistic production failure | Test? | Error handling? | User impact |
|---------|-------------------------------|-------|-----------------|-------------|
| list query | malformed stored JSON in an old task row | not yet in plan | not yet explicit | could 500 the whole library |
| DTO mapping | completed task missing `current_result.title` | partial only | UI placeholder required | silent ugly card unless handled |
| list ordering | timestamps stored but not sorted descending | yes, required | n/a | library feels random and low-trust |
| empty state | zero completed tasks | yes, required | yes, design specified | user should see guided empty portfolio |

Critical gap to avoid:

- no implementation should allow one malformed completed row to crash the whole library response without a test and fallback strategy

### Malformed Row Handling

If one completed task row cannot be mapped into a valid library card:

- skip that row
- log the mapping failure
- continue returning the rest of the library items

Version 1 should not fail the entire `GET /library/works` response because of one malformed archived record.

## NOT in Scope

- search and filtering in v1
- delete / archive management controls in v1
- historical creative replay page in v1
- a separate `library_items` table
- failed or in-progress task visibility in the v1 library view

## Information Architecture

### Screen Hierarchy

Version 1 of `我的作品库` should use a **uniform card wall** as the first impression.

That means:

1. First thing the user sees: a field of works that already feels like a personal catalog.
2. Second thing the user sees: each work's identity through cover, title, source, and time.
3. Third thing the user understands: this is a persistent archive inside the workbench, not a temporary task log.

This explicitly rejects two alternatives for v1:

- no oversized "recent work" hero card at the top
- no left-side grouping taxonomy before the library has enough depth

### Page Structure

Desktop library page:

```text
+----------------------------------------------------------------------------------+
| Left Nav: 当前创作 / 我的作品库 / future sections                                |
+----------------------------------------------------------------------------------+
| Library Header: 标题 + 一句话说明 + item count                                  |
+----------------------------------------------------------------------------------+
| Card Grid: [cover + title + source + time] [cover + title + source + time]      |
|            [cover + title + source + time] [cover + title + source + time]      |
|            [cover + title + source + time] [cover + title + source + time]      |
+----------------------------------------------------------------------------------+
```

### Section Jobs

- **Left Nav**
  One job: make `我的作品库` feel like the second main mode of the product.

- **Library Header**
  One job: orient the user that they are looking at accumulated works, not the active generation flow.

- **Card Grid**
  One job: present each song as a collectible creative artifact with clear identity.

## Card Visual Direction

The library card should use a **cover-and-metadata balanced layout**.

That means:

- the cover is visually important, but it does not consume the whole card
- metadata gets enough room to feel deliberate and legible
- the card should read like a work in a portfolio, not like a streaming thumbnail and not like a table row

Recommended card composition:

```text
+----------------------------------+
|                                  |
|            COVER                 |
|                                  |
+----------------------------------+
| 标题                             |
| 生成来源                         |
| 时间                             |
+----------------------------------+
```

Rejected directions for v1:

- **cover-dominant wall** where metadata becomes too secondary
- **info-heavy utility card** that feels like an internal asset manager

The visual read should be:

1. cover
2. title
3. source
4. time

## Grid Behavior

Version 1 should use a **regular, even card grid**.

Why:

- it reinforces the idea of a collected body of work
- it makes count and density legible at a glance
- it avoids premature "editorial" styling before grouping and series logic exist

Rejected directions for v1:

- no staggered masonry or magazine collage layout
- no single-column list treatment

Expected reading pattern:

- scan across rows
- compare covers quickly
- drop to title/source/time only after visual recognition

## Open Questions

- Should the library default to newest-first, or should it surface grouped clusters once enough works exist?
- Should failed or partial generations appear in the library, or only completed songs?
- Should clicking a card first open a lightweight detail drawer or navigate to a full archived-work page?

## Success Criteria

Version 1 is successful when:

- the user can enter `我的作品库` from the main workbench nav
- previously generated songs appear as cards
- each card clearly shows title, cover, source, and time
- the page feels like a creator portfolio, not a backend job list
- the existence of the library changes the product story from "generate one song" to "build a body of work"

### Empty State Direction

The empty state should **preserve the portfolio layout** rather than collapsing into a blank admin message.

That means:

- keep the same library header
- show 2-4 ghost cards in the exact final card proportion
- include one warm line of context:
  - `这里会保存你生成过的歌曲作品`
- include one clear primary action:
  - `去生成第一首作品`

This avoids the common failure mode where the first-time library looks like a broken or unfinished page.
